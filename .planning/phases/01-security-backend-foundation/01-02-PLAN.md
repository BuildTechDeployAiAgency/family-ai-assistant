<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> Supabase (auth) | Direct via @supabase/supabase-js; never via our serverless functions |
| Serverless function -> Postgres | RLS-enforced; user JWT passed in Authorization header to per-request client |
| Service-role -> Postgres | RLS-bypassing; restricted to cron + webhooks only (none yet — Plan 03 introduces) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information disclosure | Cross-family read via missed WHERE clause | mitigate | RLS policies on every domain table per RESEARCH Pattern 4. Test 3 proves enforcement (`cross-family document read is denied`). |
| T-02-02 | Elevation of privilege | Service-role key used in user-facing routes | mitigate | `lib/supabase.js` separates `userClient(jwt)` and `serviceClient()`; inline comment marks service-role as cron/webhook-only (D-10). Plan 03 enforces architecturally via route placement. |
| T-02-03 | Tampering | Insert with mismatched family_id (RLS-bypass attempt) | mitigate | RLS `with check` policies on insert require `family_id IN (...user's families...)`. Postgres rejects at DB layer. |
| T-02-04 | Information disclosure | RLS recursive policy performance leading to query timeouts | mitigate | All policies use `(select auth.uid())` wrapper for initplan caching per RESEARCH Pitfall 4; `idx_family_members_user` + `idx_family_members_family` indexes. |
| T-02-05 | Spoofing | User claims membership in another family via direct family_members insert | mitigate | `family_members` RLS: insert-with-check `user_id = (select auth.uid())` — user can only insert their own membership row. |
| T-02-06 | Tampering | SQL injection via supabase-js | mitigate | `@supabase/supabase-js` parameterizes all calls; raw SQL only in migration files (developer-controlled, version-controlled). |
| T-02-07 | Information disclosure | `auth.users` PII leak through `family_members` join | accept | RLS on `family_members` restricts visibility to user's own row; users can read their own auth.users (Supabase managed); no path to other users' PII through Phase 1 schema. |

</threat_model>
