# Feature 01 — Proactive reminders (attention feed + weekly digest)

## Context & why

Families using the assistant accumulate time-bounded commitments — expiring documents, approaching appointments, school tasks with due dates — but today the app surfaces these only inside their respective vertical tabs. Without a derived "needs attention" view and a low-effort weekly nudge, high-urgency items slip. v1 ships two surfaces: a client-computed **in-app attention feed** on Today (read+rank over existing rows, no new domain table) and a **weekly digest** generated by Vercel Cron using the service client (template-composed, persisted to `activity_log`, read back through a user-JWT endpoint). Push and Telegram are explicit later layers; v1 is in-app + persisted digest only.

Invariants preserved: every domain read remains `family_id`-scoped via RLS for user-JWT paths; the cron runs service-role and therefore MUST add explicit `.eq('family_id', fid)` on every query — a missing filter is a P0 cross-family leak. The OpenRouter key stays server-side (digest composition may call `api/ai/_lib` but the route itself is the only caller). `REFERENCE_DATE = 2026-05-19` is the deterministic "today" for both client ranking and cron ranking.

### `api/cron/digest.ts` (NEW — Vercel Cron, service-role)

```ts
// api/cron/digest.ts
import { serviceClient } from '../_lib/supabase';
import { env } from '../_lib/env';

const ROW_CAP = 50;

function authCron(req: Request) {
  const auth = req.headers.get('authorization') ?? '';
  const token = auth.startsWith('Bearer ') ? auth.slice(7) : '';
  if (!env.CRON_SECRET || token !== env.CRON_SECRET) {
    return new Response('Unauthorized', { status: 401 });
  }
  return null;
}

export default async function handler(req: Request) {
  const denied = authCron(req);
  if (denied) return denied;

  const sb = serviceClient();
  const today = new Date(env.REFERENCE_DATE);          // deterministic
  const in7 = new Date(today.getTime() + 7*86400_000);

  // distinct families with preferences (so we can read lead_days/digest_day)
  const { data: fams, error: fe } = await sb
    .from('preferences').select('family_id, lead_days').distinct('family_id');
  if (fe) return Response.json({ ok:false, error: fe.message }, { status: 500 });

  let written = 0;
  for (const f of fams ?? []) {
    const fid: string = f.family_id;
    const leadDays = f.lead_days ?? 30;
    const horizon = new Date(today.getTime() + leadDays*86400_000);

    // ⚠ every query MUST filter family_id — service-role bypasses RLS
    const [docs, tasks, appts] = await Promise.all([
      sb.from('documents')
        .select('title, expiry_date, status, member_id')
        .eq('family_id', fid)
        .not('expiry_date','is',null)
        .lte('expiry_date', horizon.toISOString().slice(0,10))
        .order('expiry_date', { ascending: true }).limit(ROW_CAP),
      sb.from('tasks')
        .select('title, due_date, priority, completed, member_id')
        .eq('family_id', fid)
        .eq('completed', false)
        .lt('due_date', in7.toISOString().slice(0,10))
        .order('due_date', { ascending: true }).limit(ROW_CAP),
      sb.from('appointments')
        .select('title, starts_at, category, member_id')
        .eq('family_id', fid)
        .gte('starts_at', today.toISOString())
        .lt('starts_at', in7.toISOString())
        .order('starts_at', { ascending: true }).limit(ROW_CAP),
    ]);

    const payload = {
      generated_for: today.toISOString(),
      window_days: 7,
      lead_days: leadDays,
      expiring_documents: docs.data ?? [],
      tasks_due: tasks.data ?? [],
      upcoming_appointments: appts.data ?? [],
    };

    const { error: ie } = await sb.from('activity_log').insert({
      family_id: fid,
      kind: 'weekly_digest',
      payload,
    });
    if (!ie) written++;
  }

  return Response.json({ ok: true, families: fams?.length ?? 0, written });
}
```

### `mobile/src/lib/attention.ts` (NEW selector)

```ts
// mobile/src/lib/attention.ts
export type AttentionKind = 'document' | 'task' | 'appointment';
export interface AttentionItem {
  id: string;
  kind: AttentionKind;
  title: string;
  subtitle?: string;
  date: string;             // ISO date for sorting
  urgency: 'overdue' | 'due_soon';
  daysUntil: number;
}

const NOW = () => new Date(process.env.EXPO_PUBLIC_REFERENCE_DATE
      ? Date.parse(process.env.EXPO_PUBLIC_REFERENCE_DATE)
      : Date.now());

export function computeAttention(opts: {
  documents: { id:string; name:string; number?:string|null; expiryDate?:string|null; owner?:string|null }[];
  tasks:     { id:string; title:string; dueDate?:string|null; completed:boolean; owner?:string|null; priority?:string|null }[];
  appointments?: { id:string; title:string; startsAt:string; location?:string|null }[];
  leadDays?: number;
}): AttentionItem[] {
  const today = NOW(); today.setHours(0,0,0,0);
  const lead = opts.leadDays ?? 30;
  const out: AttentionItem[] = [];

  for (const d of opts.documents) {
    if (!d.expiryDate) continue;
    const dt = new Date(d.expiryDate); dt.setHours(0,0,0,0);
    const days = Math.round((dt.getTime()-today.getTime())/86400_000);
    if (days < 0 || days > lead) continue;
    out.push({
      id: d.id, kind:'document', title: d.name,
      subtitle: d.owner ?? d.number ?? 'Document',
      date: d.expiryDate, urgency: days <= 0 ? 'overdue' : 'due_soon', daysUntil: days,
    });
  }
  for (const t of opts.tasks) {
    if (t.completed || !t.dueDate) continue;
    const dt = new Date(t.dueDate); dt.setHours(0,0,0,0);
    const days = Math.round((dt.getTime()-today.getTime())/86400_000);
    if (days > lead) continue;
    out.push({
      id: t.id, kind:'task', title: t.title,
      subtitle: t.owner ?? 'Task',
      date: t.dueDate, urgency: days < 0 ? 'overdue' : 'due_soon', daysUntil: days,
    });
  }
  for (const a of opts.appointments ?? []) {
    const dt = new Date(a.startsAt); dt.setHours(0,0,0,0);
    const days = Math.round((dt.getTime()-today.getTime())/86400_000);
    if (days < 0 || days > lead) continue;
    out.push({
      id: a.id, kind:'appointment', title: a.title,
      subtitle: a.location ?? 'Appointment',
      date: a.startsAt.slice(0,10), urgency:'due_soon', daysUntil: days,
    });
  }

  // rank: overdue first, then by date asc
  out.sort((a,b) =>
    (a.urgency === 'overdue' ? 0 : 1) - (b.urgency === 'overdue' ? 0 : 1)
    || a.date.localeCompare(b.date));
  return out;
}
```

Tradeoff note: client-side ranking ships fastest and works offline against existing stores; downside is it can't see rows the user hasn't synced. Acceptable for v1 since documents/tasks load on app open. A future `api/attention.ts` GET (user-JWT, RLS) is a drop-in if we need canonical ranking.

## Isolation & security review

- **P0 — cron cross-family leak**: `serviceClient()` bypasses RLS. Every query in `api/cron/digest.ts` carries `.eq('family_id', fid)` (documents, tasks, appointments, and the `activity_log.insert` family_id). The for-loop iterates `fams` from preferences; no query is allowed to omit the filter. Code review checklist: grep the file for `.from(` and assert each call site has `.eq('family_id'` on the same chain. A missing filter would broadcast other families' rows into every digest payload — explicit reject in PR review.
- **P0 — cron auth**: route verifies `Authorization: Bearer <CRON_SECRET>` before any work; without it returns 401. Vercel Cron injects this automatically; only our secret satisfies it. Secret length ≥16.
- **User-JWT paths unchanged**: `api/digest.ts` uses `withAuth` → RLS-scoped read of `activity_log` for the caller's family only; no service-role exposure to user requests.
- **Preferences**: new columns sit behind existing `preferences_self` policy (user may only read/update own row). `family_id` on preferences is set at signup and never client-writable.
- **No new domain table**: feed computation is pure read over RLS-scoped stores; no new write surface to attack.
- **Lead-days bounds**: 1–90 enforced both in Zod and DB CHECK; prevents pathological horizons (e.g., `lead_days=99999` bloating feed).
- **Idempotency**: weekly cron writes a new `activity_log` row per run; no unique constraint needed (append-only, latest-wins read).
